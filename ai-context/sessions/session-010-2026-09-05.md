## Tasks Completed

### 1. Sonarr queue investigation — not a bug
- 16 queued items, none moving; Sonarr showed no ETA because there was no rate to compute one from.
- Ruled out every failure mode the runbook warns about: VPN up and not leaking, port forwarding stable (44084), `max_active_torrents` fine, 2.6T free on `/incomplete`, outbound TCP working, 181 established connections.
- Root cause: **dead swarms**. Trackers reported leechers only, `num_seeds = 0` on all 114 torrents, and connected peers were stuck at the identical 99.837% (last-piece-missing).
- Underlying reason: 2000s US network TV has aged off the public indexers in use.

### 2. Cloudflare solver for gated indexers (nas-infra)
- Prowlarr had **no indexer proxy at all** (`/api/v1/indexerproxy` returned `[]`).
- Chose **Byparr** over FlareSolverr: FlareSolverr drives stock Chromium, has no Turnstile handling, unmaintained since 2023. Byparr keeps the same API and port, so Prowlarr's "FlareSolverr" proxy type points at it unchanged.
- Runs in **gluetun's namespace**, which is the non-obvious part: `cf_clearance` is bound to the IP *and* User-Agent that solved the challenge, so a solver on `media_net` would mint cookies for the NAS's WAN IP and every replay would 403 — indistinguishable from no solver.
- No `ports:`, no `FIREWALL_INPUT_PORTS` entry: Byparr is unauthenticated and fetches any URL given to it, so publishing it on the LAN would be an open proxy / SSRF pivot. Verified unreachable from `10.0.10.10`.
- Digest-pinned, because upstream tags releases on GitHub but pushes only `latest`/`main`/`nightly` to GHCR.

### 3. Indexer flapping — self-inflicted, fixed
- `mem_limit: 1g` was too tight. Camoufox opens a browser context per concurrent request; Prowlarr health-checks every tagged indexer at once.
- The kernel OOM-killed the **browser inside the container**, not the container: `RestartCount=0`, status `running`, `/health` still 200, while every in-flight solve died with `TargetClosedError` and 408'd at ~63s.
- Raised to 3g. Four concurrent solves now succeed in 8–10s at 30% of the limit; 24h later `oomkilled=false`, `restarts=0`, 11% memory.
- The three "erroring" indexers were **three different problems**, only one of which was the flapping: 1337x (the OOM), ExtraTorrent/kickass (bare 146-byte nginx 403 from the origin — not a Cloudflare challenge, so Prowlarr never routes it to the solver), RuTor (gluetun's `BLOCK_MALICIOUS` DNS blocklist refusing `rutor.info`).

## Key Decisions
- **Byparr, not FlareSolverr** — FlareSolverr would have installed cleanly and changed nothing against current Cloudflare.
- **Solver inside the VPN namespace** — forced by `cf_clearance` IP binding, not a preference.
- **Solver published nowhere** — unauthenticated arbitrary-URL fetcher; loopback-only inside the namespace.
- **Branch's playbook beat the duplicate** — qBittorrent settings enforcement mattered more than anything the duplicate added.
- **No `--force-recreate` in the media deploy** — every image is pinned, so a changed compose changes the config hash; forcing would tear down the VPN on a no-op and never report `changed=0`.
- ExtraTorrent/kickass are an origin-level block, unsolvable by any solver setting — removed rather than chased. RuTor removed rather than unblocking a malicious-list domain.
- Dead SFTP smoke-test credentials in `docs/plans/2026-03-08-nas-migration-status.md` history left as-is: accounts are gone, repo is private.
